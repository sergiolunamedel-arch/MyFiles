Antes de seguir: ese password (p0$ooiw%7HS|k_>>) ya quedó visible en texto plano varias veces en tus capturas. En cuanto resuelvas esto, vale la pena rotarlo — no es grave en dev, pero es buena práctica.

El problema real: llevamos varias vueltas de "copié y pegué bien" que terminan en Access denied, tanto con el root de MySQL como ahora con el usuario identityiq. El patrón se repite tanto que el sospechoso ya no es "un typo tuyo" — es que pegar contraseñas con caracteres especiales ($, %, |, >) directo en vim/nano vía la terminal remota es propenso a corromperse, sobre todo si el modo "paste" del cliente SSH no está activo: vim puede interpretar alguno de esos caracteres como comando en vez de texto si el pegado no entra en modo inserción limpio.

Solución: dejar de pegar a mano y forzar el mismo valor exacto por comando, de un lado y del otro, sin pasar por el editor interactivo.

1. Resetea el password del usuario identityiq en MySQL usando un archivo, no pegado interactivo:

bash
cat > /tmp/reset_pw.sql << 'SQLEOF'
ALTER USER 'identityiq'@'%' IDENTIFIED WITH mysql_native_password BY 'p0$ooiw%7HS|k_>>';
ALTER USER 'identityiq'@'localhost' IDENTIFIED WITH mysql_native_password BY 'p0$ooiw%7HS|k_>>';
FLUSH PRIVILEGES;
SQLEOF
mysql -u root -p < /tmp/reset_pw.sql
shred -u /tmp/reset_pw.sql

El delimitador 'SQLEOF' (con comillas) evita que bash interprete el $ de tu password como variable — se escribe literal en el archivo.

2. Prueba la conexión con el password inline, sin prompt interactivo de por medio:

bash
mysql -h 127.0.0.1 -P 3306 -u identityiq -p'p0$ooiw%7HS|k_>>' identityiq -e "SELECT 1;"

Si esto conecta y regresa 1, confirmamos que el problema nunca fue el password en sí, sino cómo se estaba transmitiendo al pegarlo a mano.

3. Repite el ALTER USER para los otros dos usuarios (identityiqPlugin, identityiqah) si usan el mismo password — mismo archivo, mismo patrón, solo cambiando el nombre de usuario.

4. Actualiza iiq.properties con sed en vez de pegar en vim — esto evita el mismo riesgo de corrupción al escribir:

bash
sudo -u tomcat /opt/tomcat/webapps/identityiq/WEB-INF/bin/iiq encrypt 'p0$ooiw%7HS|k_>>'

Copia el resultado (1:ACP:...) y guárdalo en una variable, luego reemplaza las 3 líneas de golpe:

bash
ENC='1:ACP:PEGA_AQUI_EL_RESULTADO_EXACTO'
sudo sed -i "s|^dataSource.password=.*|dataSource.password=${ENC}|" /opt/tomcat/webapps/identityiq/WEB-INF/classes/iiq.properties
sudo sed -i "s|^pluginsDataSource.password=.*|pluginsDataSource.password=${ENC}|" /opt/tomcat/webapps/identityiq/WEB-INF/classes/iiq.properties
sudo sed -i "s|^dataSourceAccessHistory.password=.*|dataSourceAccessHistory.password=${ENC}|" /opt/tomcat/webapps/identityiq/WEB-INF/classes/iiq.properties

5. Verifica que quedó igual en las 3 líneas:

bash
sudo grep -E '^(dataSource|pluginsDataSource|dataSourceAccessHistory)\.password=' /opt/tomcat/webapps/identityiq/WEB-INF/classes/iiq.properties

6. Reintenta:

bash
sudo -u tomcat /opt/tomcat/webapps/identityiq/WEB-INF/bin/iiq console
import init.xml
quit

Corre el paso 2 primero y dime si el SELECT 1; conecta — con eso confirmamos que el fix de raíz fue el pegado, no el password.
